# 自动化测试完善计划

> **定位：** 本文是可分阶段开工的迭代计划，不是一次性铺开的测试体系愿景。每一阶段都有固定产物、命令、环境与停止条件；未满足前置条件不得提前扩展后续范围。

> **执行记录（2026-08-05）：** P0/P1 的本地实现与验证已完成，Windows CI 与发布构建验证已加入；`npm run test:e2e:poc`、`npm run test:e2e`、`npm run test:coverage`、`npm run test:benchmark` 和 `npm run tauri:build` 已在本机通过。`cargo fmt --check` 仍是存量格式差异，Windows runner 尚未由本机执行确认；P2.1 完整阅读器回归和 P2.2 的 EPUB 基准仍未完成，不能标记为已覆盖。

## 目标

在不改变原生 ES 模块、Tauri 桌面壳、直接 DOM 架构、`http://127.0.0.1:2333` 固定 origin 和既有存储格式的前提下，分阶段补齐自动化测试。

优先保护高风险流程：原生文件授权边界、窗口状态、应用启动、TXT 导入、打开阅读和阅读进度恢复。阅读器完整回归、运行时性能基准和人工矩阵收敛放在基础能力稳定之后。

## 当前基线

### 已有能力

- `npm test` 通过 `scripts/test-all.mjs` 串行发现并运行 `scripts/test-*.mjs`、`scripts/test-*.cjs`。
- `scripts/test-test-discovery.mjs` 已验证 `.mjs`、`.cjs` 测试发现，以及夹具、辅助模块和普通脚本不会被误运行；不重建另一套发现规则。
- Node 内置 `node:test` 已覆盖 IndexedDB、迁移、目录生成、Worker 容错、EPUB 资源生命周期、阅读保存队列及部分导入逻辑。
- `cargo test --manifest-path src-tauri/Cargo.toml` 已覆盖部分窗口状态与路径判断。
- `.github/workflows/verify.yml` 当前在 Linux 执行 `npm test`、活跃 `.js` 文件语法检查和 Rust 测试。
- `npm run test:performance` 是源码结构回归检查，不是运行时性能基准。
- `docs/testing.md` 已有人工回归矩阵；后续仅在该文档中整理和收敛，不新建重复的人工清单文档。

### 已确认限制

- 活跃前端和发布包均使用 `http://127.0.0.1:2333`。更换 host 或 port 会得到另一份 IndexedDB/localStorage，不是合法的测试隔离方式。
- 原生配置数据位于应用数据目录中的 `app-config.json` 与 `import-folders.json`；必须与测试数据隔离。
- 当前未引入桌面端 E2E 驱动、浏览器自动化框架或覆盖率工具。
- 现有 CI 仅覆盖 Linux，未覆盖 Windows 主目标环境。

## 全局约束

- 活跃前端仅修改 `app_unpacked/src/`；桌面壳仅修改 `src-tauri/src/`。
- 保持原生 HTML、CSS、ES 模块和 Tauri 架构；不引入 React、Vue、全量 TypeScript 或多套重复测试框架。
- 不改变书籍、设置、迁移、原始文件恢复和 `folderId` 的数据格式或业务语义。
- 新增测试优先验证输入、输出和可观察行为。源码正则测试仅作为防止已知反模式回归的护栏。
- 先补既有行为的测试，再做为可测试性服务的最小生产代码抽取；抽取前后需由同一组行为测试证明语义不变。
- 测试不得使用真实书架、真实导入目录或默认原生应用数据目录。
- 不通过换 host、port 或 origin 隔离测试数据。
- E2E PoC 未通过前，不引入完整阅读流程自动化，也不把桌面 E2E 纳入 CI。
- 不自动提交 Git；每阶段完成后由维护者决定是否提交。

## 测试命令约定

| 命令 | 用途 | 阶段 |
| --- | --- | --- |
| `npm test` | 快速 Node 回归套件 | 已有 / 全阶段 |
| `npm run test:toc` | TXT 目录识别专项测试 | 已有 / 全阶段 |
| `npm run test:performance` | 源码结构性能回归检查 | 已有 / P2 保留 |
| `npm run test:coverage` | Node 覆盖率报告 | P1 新增 |
| `npm run test:e2e:poc` | Tauri E2E 可行性验证 | P0 新增 |
| `npm run test:e2e` | 稳定的桌面关键流程 | P1 新增 |
| `npm run test:benchmark` | 运行时性能诊断报告 | P2 新增 |
| `cargo test --manifest-path src-tauri/Cargo.toml` | Rust 单元与集成测试 | 已有 / 全阶段 |
| `cargo fmt --manifest-path src-tauri/Cargo.toml -- --check` | Rust 格式检查 | P0 新增 |
| `cargo clippy --manifest-path src-tauri/Cargo.toml -- -D warnings` | Rust 静态检查 | P0 新增 |

`test:performance` 与 `test:benchmark` 必须保持分离：前者可稳定阻止已知源码反模式；后者测量耗时和内存，仅输出诊断报告。

# P1：核心自动化保护

## P1 前置条件

- P0 已完成。
- E2E PoC 在本机和 Windows runner 可稳定运行。
- 数据隔离不会改变正式 origin、不会读写真实书架，也不会递归清理默认应用数据目录。

## P1.1：最小桌面主流程

**涉及文件：**

- 创建或修改：`e2e/` 下的测试、TXT 夹具和运行工具
- 修改：`package.json`
- 修改：`docs/testing.md`
- 可能修改：`src-tauri/Cargo.toml`

**固定流程：**

```text
启动应用
→ 书库页存在
→ 导入专用小型 TXT 夹具
→ 书库中出现预期书名
→ 打开该书
→ 阅读页标题或正文存在
→ 退出并清理专用数据
```

**实施步骤：**

- [x] 提交小型、确定性的 UTF-8 TXT 夹具；不提交用户书籍、版权内容或大体积二进制资源。
- [x] 使用 PoC 已验证的窗口定位、等待和日志策略；不另起第二套驱动层。
- [x] 导入仅使用专用临时目录与唯一测试书名，避免与测试前既有书架条目混淆。
- [x] 对异步导入和页面跳转使用状态条件等待，不使用固定长 sleep。
- [x] 失败时保留诊断物；成功后只删除已验证位于测试根目录的数据。
- [x] 将稳定流程暴露为 `npm run test:e2e`；不得合入 `npm test`，直到连续 CI 运行稳定。

**验收标准：** 开发机和 `windows-latest` 能重复执行“启动—导入 TXT—打开阅读”流程；任何失败均可定位到应用、驱动或断言阶段。

**实施顺序：**

- [ ] 翻页模式：打开、前进、后退；首页与末页 cursor 不越界。
- [ ] 滚动模式：正文出现；切换书籍或离开阅读页后旧异步渲染不继续改写当前状态。
- [ ] 目录跳转：点击目录后阅读位置/当前段落发生预期改变。
- [ ] 进度恢复：保存位置、退出、重开后恢复到预期位置或可验证范围。
- [ ] 书签：新增、删除、书签面板切换。
- [ ] 主题：浅色/深色切换后设置持久化；只断言状态或主题标识，不写像素级脆弱断言。
- [ ] EPUB：使用小型确定性夹具验证打开和正文读取；资源失败时页面不崩溃且保留既有降级语义。

每项先补能够稳定重现的测试；若失败证明生产问题存在，再将修复与对应测试放在同一小提交。不得因追求可测性对阅读器作大规模重构。

**验收标准：** 阅读器覆盖导航、目录、进度恢复、书签、主题和 EPUB 基本打开；测试在 Windows CI 连续稳定后才标记为自动化保护。

## 阶段门禁与执行顺序

```text
P0.1 基线与文档
  ├─ P0.2 Rust 原生边界测试
  └─ P0.3 E2E PoC
        └─ 仅 PoC 可行且隔离安全 → P1.1 最小桌面流程
                                     ├─ P1.2 Windows CI / 构建验证
                                     └─ P1.3 覆盖率基线
                                           └─ P2.1 阅读回归
                                                ├─ P2.2 性能基准
                                                └─ P2.3 人工矩阵收敛
```

- P0.2 与 P0.3 可以并行，但不可同时修改同一份 CI 或包管理文件。
- P1.2 的 Windows 快速 CI 可在 P1.1 开发期间准备，但 E2E job 只能在 P1.1 稳定后启用。
- P1.3 覆盖率与 P1.1 独立，但应在 P1 结束前完成，避免后续阅读测试没有基线。
- P2 只在 P1 的 E2E、Windows CI 和覆盖率基础稳定后开始。
